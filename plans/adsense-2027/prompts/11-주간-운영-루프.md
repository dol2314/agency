# 프롬프트 11 — 주간 운영 루프 (매주 월요일)

## 목표
지표를 보고 이번 주 할 일 3개를 정한다. 감으로 글을 늘리지 않는다.

## 운영자 작업 (실행 전, 10분)
`docs/weekly/YYYY-MM-DD/` 폴더에 내보내기 파일을 넣는다.
- 서치콘솔: 실적(페이지·검색어, 최근 28일·직전 28일), 페이지 색인 생성 보고서, 생성형 AI 실적 보고서(있으면)
- 네이버 서치어드바이저: 사이트 현황·검색 유입 키워드
- 애드센스: 페이지별 보고서(페이지 RPM, 노출수, 클릭수), 최근 28일
- GA4: 이벤트(calc_complete, next_action_click, calendar_add, app_install_click), 페이지별 세션
- (앱 출시 후) Play Console 설치·유지, AdMob 수익

## Claude Code에게
```
docs/weekly/ 의 이번 주 폴더와 지난주 폴더를 읽어 비교하라.

1. 요약 표: 일 평균 방문, 방문당 PV, 페이지 RPM, 월 예상 수익, 색인 페이지 수(구글/네이버), 클릭 상위 10 검색어 — 지난주 대비 증감
2. 기획안 7장 수익 추정표(기준 시나리오)와 실제 비교. 2주 연속 보수 시나리오 아래면 경고.
3. 기회 찾기:
   a. 노출은 많은데(상위 20%) 클릭률이 낮은 페이지 → 제목·설명 개선안 2개씩
   b. 순위 8~20위 검색어 → 해당 페이지에 보강할 섹션 제안
   c. RPM 상위 5개 페이지의 공통점 → 같은 결의 새 페이지 후보
   d. calc_complete 대비 next_action_click 비율이 낮은 계산기 → 결과 화면 개선안
4. 위험 찾기: 색인 제외 급증, 특정 페이지 RPM 급락, 크롤링 오류, 정책 센터 알림(운영자가 메모로 넣은 경우)
5. 이번 주 할 일 3개를 우선순위로 제안(각각 어느 프롬프트로 실행하는지, 예상 소요 시간). 운영 시간은 주 10~15시간.
6. 결과를 docs/weekly/YYYY-MM-DD/report.md 로 저장.

파일에 없는 수치는 추정하지 말고 "데이터 없음"으로 적어라.
```
